# 2BL 營運世界樹

狀態日期：2026-08-22

這份文件不是功能清單，而是 2BL 正式系統的「實際營運路徑總導航」。

每個節點都應回答：
- 使用者現在在哪裡
- 為什麼會到這裡
- 現在能做什麼
- 下一步會去哪裡
- 哪些正式資料會被讀取／修改
- 前台、後台、Worker、Supabase 如何串接
- 現在是 PASS／VERIFY／BLOCKED／LATER／UAT／DEPRECATED 哪一種狀態

狀態定義：
- PASS：程式、正式部署與實際情境驗證都通過
- VERIFY：已上線或已完成開發，但仍需持續真人情境驗證
- BLOCKED：有已知阻擋，不能視為可用
- LATER：已定義但尚未實作
- UAT：功能已存在，等待特定角色／裝置／真實情境驗收
- DEPRECATED：已退出正式流程，不應再有可用入口

---

## 角色：會員／攤商

### 路徑：登入 → 我的紀錄 → 會員資料

會員輸入 Email＋手機完成身分驗證後，可進入自己的會員資料與歷史活動紀錄。

#### 節點：會員本人修改基本資料

- 使用者看到：姓名、手機、品牌、販售類別、FB、IG、官網／作品連結、品牌介紹。
- Email：目前仍是重要登入與歷史關聯識別，不在一般基本資料修改中直接變更。
- 手機：只有會員本人明確按儲存且確認後才允許更新。
- 背景自動儲存：只能沿用已驗證的原手機，不得靜默把尚未確認的新手機寫成登入手機。
- Worker：`saveMember`
- Supabase：更新 `members`；不更新歷史 `registrations`、`payments`、`refund_transactions`、`member_credit_ledger`、排位／每日營運紀錄。
- Audit：會員本人有實際欄位變更時，寫入 `audit_logs.action = member_profile_self_update`。
- 狀態：VERIFY
- 原因：正式 Worker 已部署且來源比對通過；仍採真實會員持續使用驗證。

## 角色：主辦方／平台管理員

### 路徑：後台 → 會員 → 搜尋會員 → 資料／修改

#### 節點：管理者協助修正會員基本資料

目標：會員因不熟悉手機操作、填錯電話或其他基本資料時，主辦可直接協助修正，不必每次由工程端進資料庫處理。

- 入口：`admin.html` →「會員」→ 搜尋品牌／姓名／手機／Email →「資料／修改」。
- 可修改：姓名、手機、品牌名稱、販售類別、Facebook、Instagram、官網／作品連結、品牌介紹。
- Email：唯讀，不在此流程修改。
- 儲存前：顯示「原資料 → 新資料」供管理者確認。
- 前端 action：`adminUpdateMemberProfile`
- Worker：`hAdminUpdateMemberProfile`
- 權限：必須具備 `canManageMembers`；系列管理者只能處理自己被授權系列內曾有報名的會員。
- Supabase 正式寫入：只更新 `members` 的基本欄位。
- 不應被本功能覆寫的資料：
  - `registrations`
  - `payments`
  - `refund_transactions`
  - `member_credit_ledger`
  - 攤位／排位資料
  - 每日報到／撤場／押金狀態
  - 財務紀錄
  - 歷史活動紀錄
- Audit：寫入 `audit_logs.action = admin_member_profile_update`，保存修改前、修改後、操作者與變更欄位。
- 重新讀取：儲存成功後重新載入正式 `members` 資料，不以前端暫存當成完成。
- 修改紀錄入口：會員詳情 →「查看修改紀錄」→ `getMemberEditHistory`。
- 正式部署：已完成。
- 正式 Worker version：`3b383dff-d161-41bb-bd55-5e1942107c1f`
- 正式 Worker SHA-256：`65262f02565e938a03bf8a9e660f7d4ff62e221797a1081809a56231ea858bd3`
- 正式 Supabase tenant：`tuibile`
- 正式資料契約：0 unknown tables、0 unknown routines、0 blockers。
- 目前真人進度：管理者已於正式後台完成一次會員資料修正操作。
- 狀態：VERIFY
- 驗證原則：若後續真實使用發現登入、歷史紀錄、付款、活動金或排位異常，立即把本節點降為 BLOCKED／VERIFY 並修正；在未發現問題前維持已上線可用狀態。

## 角色：主辦方／平台管理員

### 路徑：後台 → 場次／待辦 → 主辦代報名／延期轉場

#### 節點：主辦代報名多日日期操作

- 入口：主辦代報名。
- 多日場次：日期以可操作的「勾選框＋日期＋正式費用」方式逐日顯示。
- 選取日期：沿用既有 `amrDate`／`selectedDates` 正式流程，不另造第二套資料來源。
- Worker：既有主辦代報名 preview／save handler。
- Supabase：新報名只保存實際勾選日期；既有報名、付款、退款、活動金、押金、排位與財務資料不因本修正被重算或覆寫。
- 正式情境驗證：已由管理者於正式系統完成操作驗證。
- 狀態：PASS

#### 節點：多日場次延期／轉場可選實際轉入日期

- 入口：報名處理 → 延期／轉移場次。
- 操作：先選目標場次，再勾選要轉入的一天或多天。
- Worker：只接受目標場次正式 `sessions.dates_json` 內存在的日期；日期不屬於目標場次時阻擋。
- 正式計算：依實際勾選日期重新計算目標場活動費、押金、應補差額與可轉活動金。
- 新報名：只保存實際選取的 `selected_dates_json`。
- 每日營運：未來新建立的轉場報名，由正式 DB trigger 同步建立 `registration_day_ops`；不回填、不 UPDATE／DELETE 既有 registrations。
- Tenant 隔離：trigger 只作用於 `tenant_id = tuibile`。
- 原功能保留：活動金、退款、押金、設備、排位、財務與既有轉場／取消入口未被移除。
- 正式情境驗證：已由管理者於正式系統完成操作驗證。
- 狀態：PASS

## 此節點的失敗預想與防護

1. 改手機後歷史活動消失
   - 預防：Email 不在一般修正流程直接修改；本功能只更新 `members`。
   - 驗收：重新登入後檢查歷史活動、付款、退款、活動金、排位。

2. 背景儲存偷偷改手機
   - 預防：silent/background save 強制沿用已驗證舊手機。
   - 驗收：修改手機輸入但未明確儲存，不得變更正式登入手機。

3. 管理者改錯資料後無法追查
   - 預防：每次實際變更寫 `audit_logs` 前後值與操作者。
   - 驗收：後台「查看修改紀錄」能讀到正式歷程。

4. 系列管理者跨系列改會員
   - 預防：Worker 中央權限與會員所屬報名場次範圍驗證。
   - 驗收：不在授權系列內的會員應被拒絕。

5. 改基本資料連帶破壞付款／退款／活動金／排位
   - 預防：handler 只對 `members` 執行 update；其他正式表不在此寫入流程。
   - 驗收：修改前後比對相關正式紀錄數量與狀態。

6. 多日代報名日期版型壞掉
   - 預防：日期選項保留正式 `amrDate`／`selectedDates` 接線，只修可操作版型。
   - 驗收：逐日勾選、費用顯示、送出後正式保存與重讀一致。

7. 轉場被迫整場全部日期
   - 預防：前端明確送出 `targetDates`；Worker 以目標場次正式日期白名單驗證。
   - 驗收：單日、多日、只選其中一天、多選日期皆能建立正確新報名。

8. 轉場後現場報到資料缺失
   - 預防：新轉場報名 insert 時，由 DB trigger 同交易建立所選日期的 `registration_day_ops`。
   - 驗收：新場每日報到／撤場／押金狀態可被正式讀取。

## 後續維護規則

任何新功能、入口、狀態或流程變更，都要先放回實際角色路徑，再補：

角色 → 使用者操作 → 前台／後台畫面 → API action → Worker handler → Supabase 正式資料 → 狀態恢復 → 其他關聯資料 → 失敗處理 → 驗收狀態。

本文件是 2BL 營運世界樹的正式定義起點；工程模組表只能作為節點展開細節，不再把模組清單本身稱為「世界樹」。
